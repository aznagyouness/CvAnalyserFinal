
# Structured Log Example Explanation

This document explains the structured log output from your application, including both successful logs and an example error log.

---

## 1. Plain Text Startup Messages (Non-Structured)
These first couple of messages are plain text, likely printed directly with `print()` or similar:
```
settings loaded.
✅ Database Engine and Session Factory initialized.
✅ Global Quota Managers initialized.
```

---

## 2. Structured Log Event 1: Taskiq Middleware Connected
Now we get to the good stuff—structured JSON logs! Let's look at the first one:
```json
{
  "env": "dev",
  "event": "TaskiqIdempotencyMiddleware connected to Redis",
  "func_name": "startup",
  "lineno": 68,
  "logger": "src.utils.taskiq_idempotency",
  "module": "taskiq_idempotency",
  "service": "essai-for-celery",
  "severity": "INFO",
  "timestamp": "2026-07-21T12:50:04.613012Z",
  "version": "0.1.0"
}
```

### Field Explanations:
- **`env`**: "dev" (matches your `ENV` variable in [.env](../.env#L12))
- **`event`**: The main log message ("TaskiqIdempotencyMiddleware connected to Redis")
- **`func_name`**: Name of the function where the log was emitted ("startup")
- **`lineno`**: Line number in the file (68)
- **`logger`**: The logger name ("src.utils.taskiq_idempotency") (from `__name__` in the logger creation `logger = get_logger(__name__)`) (for example, in [src/utils/taskiq_idempotency.py](../src/utils/taskiq_idempotency.py))
- **`module`**: The Python module ("taskiq_idempotency") The `module` field shows the **name of the Python file (without the path or .py extension)** where the log was emitted.
- **`service`**: Your app name ("essai-for-celery", from `APPNAME` in [.env](../.env#L10))
- **`severity`**: Log level ("INFO"—note we renamed `level` to `severity` in [logging.py](../src/observability/logging.py#L527) for OpenTelemetry/Grafana compatibility!)
- **`timestamp`**: ISO 8601 UTC timestamp of when the log was created
- **`version`**: App version ("0.1.0", from `APPVERSION` in [.env](../.env#L11))

## 5. Structured Log Event 4: Custom Info from Ping Route
This is the log from your `/api/v1/welcome/ping_structlog` route. Notice the extra fields:
```json
{
  "env": "dev",
  "event": "warinig is comming",
  "func_name": "ping",
  "lineno": 221,
  "logger": "src.routes.welcome",
  "method": "GET",
  "module": "welcome",
  "path": "/api/v1/welcome/ping_structlog",
  "service": "essai-for-celery",
  "severity": "INFO",
  "status": 200,
  "test": "success",
  "timestamp": "2026-07-21T12:50:15.422067Z",
  "trace_id": "3a455dc5-63ac-445e-8769-9fe492d270b4",
  "version": "0.1.0"
}
```

### New Fields Here:
- **`method`**: HTTP method (GET)
- **`path`**: Request path ("/api/v1/welcome/ping_structlog")
- **`status`**: HTTP status code (200)
- **`test`**: A custom field you added ("success")
- **`trace_id`**: Generated by our RequestContextMiddleware (from [middleware.py](../src/observability/middleware.py))—this lets you trace all logs from the **same request!**

## 6. Structured Log Event 5: Uvicorn Access Log
The final log is the Uvicorn access log, also captured by our structlog config and enriched with the same fields (including `trace_id`!):
```json
{
  "env": "dev",
  "event": "127.0.0.1:57624 - \"GET /api/v1/welcome/ping_structlog HTTP/1.1\" 200",
  "func_name": "send",
  "lineno": 483,
  "logger": "uvicorn.access",
  "method": "GET",
  "module": "httptools_impl",
  "path": "/api/v1/welcome/ping_structlog",
  "service": "essai-for-celery",
  "severity": "INFO",
  "timestamp": "2026-07-21T12:50:15.423735Z",
  "trace_id": "3a455dc5-63ac-445e-8769-9fe492d270b4",
  "version": "0.1.0"
}
```
### 1. Your Custom Route Log (from src.routes.welcome)
- What it is : A log you explicitly add in your route handler (e.g., logger.warning("warinig is comming", test="success") ).
- What it's good for :
  - Tracking custom business logic (e.g., "user uploaded a document", "payment processed successfully").
  - Adding custom fields (like test: "success" or user_id: "123" ).
  - Logging things Uvicorn doesn't know about (e.g., internal function calls, database queries).
### 2. Uvicorn Access Log (uvicorn.access)
- What it is : An automatic log Uvicorn adds for every single HTTP request (even if you don't write any code).
- What it's good for :
  - Tracking every HTTP request/response (even for routes you don't add custom logs to).
  - Getting consistent info for all routes (client IP, status code, etc.).
  - Monitoring traffic patterns (how many requests per minute, which routes are most popular).

### Our Recommendation
Keep both! Here's why:

1. Uvicorn access logs : Give you a complete picture of all HTTP traffic.
2. Your custom logs : Give you detailed business context for specific events.
3. Trace ID : Links them together, so you can see the full story of a single request!
If you did want to disable Uvicorn's access log, you'd run Uvicorn with --no-access-log , but we'd recommend keeping it for now! 😊

## 6.1 Understanding Uvicorn's Internal Loggers

Uvicorn uses two internal loggers that our structlog configuration automatically captures and enriches with our structured fields!

### 1. **`uvicorn.access` Logger**
- **What it logs**: Access logs for every HTTP request (like Nginx/Apache access logs).
- **Example from your logs**:
  ```json
  {
    "env": "dev",
    "event": "127.0.0.1:57624 - \"GET /api/v1/welcome/ping_structlog HTTP/1.1\" 200",
    "logger": "uvicorn.access",
    "method": "GET",
    "path": "/api/v1/welcome/ping_structlog",
    ...
  }
  ```
- **What you can get from it**:
  - Client IP address
  - HTTP method (GET/POST/etc.)
  - Request path
  - HTTP status code
  - Response time (if you set it up!)
  - Request/response size

### 2. **`uvicorn.error` Logger**
- **What it logs**: Errors, warnings, and general info from Uvicorn itself (startup, shutdown, server errors).
- **Example from your logs**:
  ```json
  {
    "env": "dev",
    "event": "Application startup complete.",
    "logger": "uvicorn.error",
    ...
  }
  ```
- **What you can get from it**:
  - Application startup/shutdown events
  - Server errors (5xx errors)
  - Uvicorn-specific warnings (e.g., deprecated options)

### Why This is Great!
Our structlog configuration in [logging.py](../src/observability/logging.py) automatically:
1. Captures all logs from `uvicorn.access` and `uvicorn.error`
2. Adds our structured fields (like `service`, `env`, `trace_id`)
3. Formats them as JSON!

This means you don't have to parse messy plain text access/error logs—everything is structured!
For 99% of cases, you only need to care about:
- uvicorn.access : For HTTP request logs
- uvicorn.error : For errors and startup/shutdown events

we have also uvicorn.asgi : For ASGI logs, uvicorn.lifespan : For lifespan events, uvicorn.config : Logs related to Uvicorn's configuration (rarely used)

## 7. Example Error Log (What Could Go Wrong)
Here's an example of what a structured error log would look like, complete with a traceback:
```json
{
  "env": "dev",
  "event": "Failed to process document",
  "exception": {
    "type": "ValueError",
    "value": "Document too large",
    "module": "src.services.document_processor",
    "frames": [
      {
        "file": "src/services/document_processor.py",
        "line": 42,
        "function": "process",
        "code": "if size &gt; MAX_SIZE: raise ValueError(\"Document too large\")"
      },
      {
        "file": "src/routes/documents.py",
        "line": 123,
        "function": "upload_document",
        "code": "await processor.process(file)"
      }
    ]
  },
  "func_name": "process",
  "lineno": 42,
  "logger": "src.services.document_processor",
  "method": "POST",
  "module": "document_processor",
  "path": "/api/v1/documents/upload",
  "service": "essai-for-celery",
  "severity": "ERROR",
  "timestamp": "2026-07-21T13:00:00.123456Z",
  "trace_id": "abc123-def456-ghi789",
  "user_id": "user_123",
  "version": "0.1.0"
}
```

### Key Error-Specific Fields:
- **`exception`**: Structured traceback (including exception type, message, and stack frames)
- **`user_id`**: Example of a custom context field you might add for user-specific errors
- **`severity`**: "ERROR" (for critical issues)

## 8. Log Severity Levels
Here are the common severity levels (from least to most critical):

1. **`DEBUG`**: Detailed information, usually only useful for debugging.
2. **`INFO`**: General information about the application's normal operation (e.g., startup, successful requests).
3. **`WARNING`**: Something unexpected happened, but the application is still working (e.g., a deprecated API is used, a retry is attempted).
4. **`ERROR`**: An error occurred, but the application can continue running (e.g., a single document failed to process).
5. **`CRITICAL`**: A serious error occurred, and the application might need to shut down (e.g., database connection lost, out of memory).

---

### 8.1 How to Spot a Problem
- **If you see `WARNING`**: Something is off, but it's not critical yet. Worth checking!
- **If you see `ERROR`**: Definitely a problem—something broke, but the app is still running.
- **If you see `CRITICAL`**: Big problem—your app might be crashing!

## Key Takeaways:
1. **All logs (even from Uvicorn and third-party libraries!) are now structured JSON**—this is exactly what we set up in [logging.py](../src/observability/logging.py).
2. **Every log has consistent metadata**: `service`, `env`, `version`, `timestamp`, `severity`.
3. **Request-scoped context (`trace_id`, `method`, `path`) is automatically added** by our middleware!
4. **You can add custom fields** (like `test: "success"` or `user_id: "user_123"`) easily by passing them as keyword arguments to the logger!
5. **Errors include structured tracebacks**, making debugging way easier in production!
